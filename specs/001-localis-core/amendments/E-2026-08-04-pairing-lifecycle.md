# Amendment E — 配对生命周期的四处澄清

**日期**: 2026-08-04
**状态**: 已采纳
**触发**: #31 首次对真 bridge 联调、#30 实现 401 处理时暴露的契约自相矛盾，以及 #33。

---

## 为什么是「澄清」而不是「新增」

四条都不是新决定。前三条都是**契约没写下来、而两侧各自按自己的理解实现了**的东西——
其中两条两侧理解一致（所以从没冲突过，也就从没被发现），一条两侧理解不同
（散文与表格互相矛盾，实现跟了散文）。

这本身是本修正案最值得记住的部分：**契约的沉默不会产生冲突信号。** 两边各写各的、
各自全绿，直到有人把它们接起来。#31 就是那个「接起来」的时刻，它一次性暴露了这三条。

第四条（§4）不同：它两侧都没有误解，是一份**准确的报告加上一个没被测的变量**。
保留在同一份修正案里，因为它同样是「只有真连接才会问到的问题」。

---

## §1 只有 `token_revoked` 清凭据，`invalid_token` 不清

**矛盾**：散文（:118）只说被吊销的 token 返回 `token_revoked` 时清除；错误码表（:587）
把两个码并列写成同一行「清除 token，提示重新配对」。iOS 实现跟的是散文。

**裁决：收窄表格，以散文与实现为准。**

理由不是严重程度，是**原因空间**：

- `token_revoked` 携带「有一件已知的事发生过」——人在 Mac 上执行了吊销。
- `invalid_token` 的成因是开放的：bridge 重启、状态丢失、实现缺陷、还没想到的第四种。

为一个说不清的拒绝清掉 Keychain，不可逆程度高于放弃一次操作，而用户拿不到任何
能据以判断「该不该重新配对」的信息。

**由此产生一条 bridge 侧的义务**：只对走过吊销流程的 token 发 `token_revoked`，
其它任何认不出的 token 一律发 `invalid_token`。**这条约束客户端无法弥补**——
两个码在线上长得一模一样，客户端只能相信。

**已知的落地缺口（不是本修正案要解决的）**：截至今日，bridge 三个 401 发射点全发
`invalid_token`，`token_revoked` 零发射源；`TokenStore.revoke(deviceID:)` 零生产调用者。
iOS 侧接收端已实现并有变异证明。也就是**两侧各写了一半，中间没有线**。
unpair 路由的实现另行派工。

## §2 token MUST 持久化，bridge 重启不解除配对

**缺口**：契约从没写过 token 的生命周期。bridge 把它放在内存里，重启即失效——
每次重启都在无声地解除所有设备的配对。

**裁决：这是转写遗漏，不是有意的留白。**

spec:46 说「做一次配对」，spec:220 说换址后「不要求重新配对」，FR-027 把解除配对
定义成一个**显式动作**。三处合起来只支持一种读法。

最锋利的一条论据是反证：**若重启等于解除配对，FR-027 描述的那个显式动作就没有意义了**——
它要保证的那个状态，每天被无声地重置若干次。一条 MUST 若能被无关操作顺手实现，
它就不是一条 MUST。

## §3 配对请求本身就在已 pin 的连接上发出

**误解**：契约（:43）说「客户端在配对时记录 SPKI」，被读成「配对时还没有 pin，
所以配对这一跳必须允许无 pin 连接」。iOS 侧据此保留了 `PinnedHTTP(pin: nil)` 的
可能性，并把 `PinnedTrust.evaluate` 对 nil pin 返回 `.refuse` 当成一个待修的洞。

**裁决：文档措辞误导，实现是对的，不用改。**

SPKI 与 6 位码走**同一条带外渠道**（Mac 屏幕）。配对发起时两者都已在手，
所以配对请求可以、且应当在已 pin 的连接上发出——这比先裸连再记录严格更强。

**证据**（#31 实测，非推断）：`pairingThenModels` 用的是 `PinnedHTTP(pin: pin)`，
它走到了 `.pairingCodeRejected`。该错误全仓只有一个抛出点（`BridgePairing.checkStatus`
的 `case 401`），只能在 `perform` 已返回 `HTTPURLResponse` **之后**到达。也就是说
带 pin 的连接握手成功了，bridge 给了 HTTP 401。**一个 401 证明了 TLS 通了。**

因此 `PinnedTrust.evaluate` 对 nil pin 返回 `.refuse` 是正确行为，不是缺路径。
契约补一句，把「不存在无 pin 那一步」写明。

## §4 鉴权先于路由：401 遮蔽 404/405 是有意的

**报告**：bridge 侧观察到无 token 时 `GET /nope` 返回 401 而非 404，
`GET /localis/v1/pair`（方法错）返回 401 而非 405；担心契约 §6 的 404/405
成为客户端永远拿不到的死码。

**裁决：保持现状。但结论要收窄一档——两个码不是死码。**

**实测**（2026-08-04，真 bridge）：报告测的是**无 token**的场景。补上带有效
token 的对照后：

| 请求 | 结果 |
|---|---|
| `GET /nope` + 有效 token | **404** `not_found` |
| `GET /localis/v1/pair` + 有效 token | **405** `method_not_allowed` |
| `GET /nope` 无 token | 401 `invalid_token` |

所以准确的表述不是「404/405 不可达」，而是「**未鉴权调用方**拿不到 404/405」。
生产客户端配对之后始终携带 token，拿得到。

保持的理由：安全侧收益是实的（不向未鉴权调用方泄露路由表）；代价经实测证明只落在
手工探测场景（curl 忘带 header）；而「鉴权在路由分发之前」本身就是网关该有的顺序——
反过来意味着未鉴权请求能探到有哪些路径存在。

契约补一句写明这是有意的，见 §6。

**这条的方法论价值**：报告本身是可信的（正对照打出来的，不是推的），双方论据也
列全了。改变结论的是**一个没被测的变量**——带 token。加上它之后，「不可达」收窄成
「未鉴权不可达」，而两个结论对应的行动完全不同：前者要改代码，后者只补一句文档。
报告者没有漏测，无 token 本来就是他在测的那件事；这是「**同一个观察在不同对照下
支持不同结论**」，而不是谁看错了。

## 一条不属于本修正案、但由同一次联调产生的发现

iOS 侧 `PinnedHTTP.stream()` 使用 `session.bytes(for:)`，其 async 变体**不经过
session-level delegate**，pinning 从未被调用，自签名证书直接 `-1202`。而产品里
**只有配对走 `perform`，其余全部走 `stream`**。

这不是契约问题（契约没说错任何一句），是实现问题，记为任务 #32。写在这里只为
说明为什么这四条澄清是在今天、而不是更早或更晚被发现的：**它们都需要一次真正的
端到端连接才会显形**，而那次连接直到今天才第一次发生。
