**用户原话**：

> skills 重点解决输入可以快速引用的痛点，不需要很复杂的功能

---

## 0. 一句话

**Skills 不是一个子系统，是输入框里的一个加速器。**
全部职责：**打 `/` → 快速找到 → 文本进输入框 → 自己改 → 发送。** 到此为止。

原 spec 把它建成了一个带参数 schema、表单校验、调用溯源、历史重发的子系统。**砍掉。**
砍掉之后它不再是「一个 story」，而是「输入框的一个功能」。

标 **[B]** 的内容为本修正案引入或修改。

---

## 1. 砍掉什么，为什么

| 砍掉 | 原条目 | 为什么 |
|---|---|---|
| **参数表单 + 必填校验** | FR-021、`ParameterValidator`、US4 场景 2 | **输入框本身就是参数机制。** 模板里的 `{{topic}}` 原样插进输入框，用户直接打字覆盖它。多一层表单 = 多一层 UI、多一套校验、多一批状态——为了一件「选中文字再打字」已经完美解决的事。 |
| **`skillInvocation` 溯源** | FR-022 后半、`SkillInvocation` 实体、T064 | 文本一旦进了输入框、被用户改过，**它就是一条普通消息**。追踪「这条消息源自哪个 skill」既不准（用户改了什么无从得知）也无人需要。 |
| **「同 skill 重发（参数预填）」** | US4 场景 4、T066 | 依赖上面那条溯源。且真实操作是：再打一次 `/`，两秒的事。 |
| **`{{name}}` 变量替换（`PromptExpander`）** | FR-022 前半、T061 | 没有参数表单就没有「参数值」可替换。**插入的就是模板原文。** 整个展开器消失。 |
| **`SkillParameter` 建模** | 实体表、`SkillDescriptor.parameters` | 见 §2 的取舍。**结论：不建模。** |
| **capability 门控 skill 入口** | FR-013 的 skill 部分、US2 场景 4、T067 | 见 §3 的取舍。**结论：不门控。** |

**保留的就是全部功能**：从 bridge 拉目录（FR-020，Mac 仍是唯一真源）、`/` 触发行内选择器、
**输入即模糊过滤**、选中插入为可编辑文本、逐条容错解析（FR-023）、空态。

## 2. `SkillParameter` — 决定：不建模

`SkillDescriptor` 收缩为 **`id` / `name` / `summary?` / `template`**。

**理由**：唯一还需要「知道哪里有占位符」的场景是**把光标停在第一个占位符上**——而这只需要对
`template` 扫一遍 `{{...}}`，一个纯函数、零元数据。为此维护一套
`kind`（text/multiline/enum/bool）/ `label` / `isRequired` / `defaultValue` 的类型，
是为一个不存在的表单供养一套 schema。

**线上格式不变**：`/v1/skills` 仍**允许**返回 `parameters`（以及 `backends`），
**客户端 v1 一律忽略**——这正是 FR-023 前向兼容规则的既有行为，不是新规则。
好处：**bridge 端不需要任何改动**，且日后真要做表单，把字段读起来即可，**无需改协议**。

---

## 3. capability 门控 — 决定：不门控，`/` 永远可用

**理由**：插入 skill 是**纯客户端的文本操作**。文本进了输入框之后，它就是一条普通 user message——
**任何**后端都能接收一段文本。要求后端声明 `skills` 能力才允许用户「往输入框里插一段字」，
是把一个客户端行为绑在一个服务端声明上，没有对应关系。

同理，`SkillDescriptor.backends`（该 skill 适用于哪些后端）**v1 也不用于隐藏**——
它是作者的建议，不是权限。隐藏一个用户 Mac 上确实存在的 skill，只会让人以为它丢了。

**因此**：
- `/` 选择器在**目录非空**时始终可用，不看 capability。
- `Capability.skills` 仍保留在枚举里（bridge 可能照发，解析照收），但**不再驱动任何 UI**。
- **FR-013 不删除**——它对 `workspace` 等仍然成立。只是把 skill 从它的例子里拿掉。

> 与宪法 IV 无冲突：IV 禁止的是**按 backend 名字**分支；「不做门控」不是名字分支。

## 4. 多主机交接（Amendment A 提出的问题，此处回答）

`/v1/skills` 是**逐主机**的——skill 是那台机器上的文件。

- **目录逐 host 缓存**，键为 `hostID`。会话的 `/` 选择器只显示**该会话所属主机**的 skill
  （由 FR-030 的会话-主机绑定直接推出）。
- **两台机器上有同名 skill** → 互不干扰，各归各的主机（与后端的复合键规则同源）。
- **主机不可达时 `/` 怎么办**（明确选一个并写死）：
  **供应本次进程内最后一次拉到的缓存；进程内从未连上过则显示空态**
  （文案：「连上 <主机名> 后才能加载 skill」），**不报错、不转圈**。
- **缓存只在内存，不落库。** 取舍说明：落库能让「重启 App 后离线也能插 skill」成立，
  但要为一个便利引入一张表 + 一次迁移 + 一条「模板可能含路径，不得进日志」的隐私面。
  v1 不值。**日后要做是纯增量改动**（加一层持久化，无协议、无模型变更）——故意留的口子，
  不是遗漏。

## 5. 优先级与体量

**US4 仍标 P2**——它依旧不是 tracer bullet 的一部分。但两件事变了，且比标签更重要：

1. **体量**：Phase 6 从 **8 票压到 4 票**（T060/T062/T063/T065），
   `ParameterValidator`、`PromptExpander`、溯源持久化、重发 UI、capability 门控**全部消失**。
2. **阻塞边**：它不再等 US2 的 capability 接线（原 T067 依赖 T043）。
   现在只要 US1 的通道在（T025/T027），**随时可插队做完**——半天的事。

## 6. 合宪性

无原则冲突。逐条：

| 原则 | 结论 |
|---|---|
| **I. 密钥零上设备** | 不变。skill 模板是用户自己写的 prompt 文本，非凭据。**但**模板可能含路径 → 沿用零日志规则：不得进 os_log / 崩溃上报。§4 的「只在内存」还顺带缩小了这个面。 |
| **III. SPM 分层** | `SkillsKit` **不删包**（它仍拥有解析与容错），只是变薄。不新增包，依赖方向不变。 |
| **IV. 单一协议** | **协议零改动**（`parameters`/`backends` 仍可被 bridge 发送，客户端忽略）。不 bump 版本。不引入 backend 名字分支。 |
| **§边界校验** | FR-023 逐条容错**保留**——它是本次唯一保留的「复杂度」，因为它便宜且防止一条坏数据搞掉整张列表。 |
| **§测试** | 「skill 展开」退出强制 TDD 区（**该逻辑已不存在**），由「skill 解析容错」顶替。 |

  它不迁移会话，是新建，符合 FR-030。
