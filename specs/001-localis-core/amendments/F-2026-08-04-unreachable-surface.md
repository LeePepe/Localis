# Amendment F — 不可达状态的告知位置

**日期**: 2026-08-04
**状态**: 已采纳
**触发**: #35 实现前的规格核查。store 去找依据，发现**这一端根本没有 FR**。

---

## 缺口

任务 #35 的标题是「不可达原因到 host 列表」——**那半句是 team-lead 拍的，不是规格要求的**。
去查依据时发现：

- **FR-053**（Amendment C）只说「主机不可达的**会话**，其**输入框** MUST 可见地禁用并说明
  原因」。这一端**已经实现**（`ComposerState` 的 `canSend` + `blockedReason`）。
- **宪法 V** 规定证书不匹配「即拒连、不弹继续信任」，但**没规定在哪告知用户**。
- 派生态那一行（**[B]**）规定了 `reachability` **不是什么**（不持久化），没规定它**显示在哪**。

也就是说：`session.status` 那条线（输入框）通了，host reachability 这条线（列表）
**从来没有被要求过存在**。而 `HostRuntimeState` / `HostReachability` /
`HostUnreachableReason` 三个类型已经写好了，零生产写入方、零读取方。

**这是「给一个类型找消费者」而不是「给一个需求找实现」**——正是 AGENTS.md 规则 7
警告的那件事，只是这次发生在下任务的人身上而不是实现的人身上。

## §1 FR-060：告知位置是 host 列表

**决定：规格漏了，补上。不是把 #35 改成挂输入框。**

决定性论据是一个**输入框那条线覆盖不到的场景**：

> **一台主机可能一个会话都没有。**

刚配对完就换了证书，是最典型的情形，也恰恰是**最需要告知**的情形——配对是刚发生的，
用户对「我刚连的这台机器身份变了」最有判断力。而没有会话就没有输入框，方案「全部走
FR-053 那条线」在这个场景下**没有任何告知路径**。

补强：spec.md 的多主机叙事本来就描述了「其中一台关机了」，主机可用性本就是列表这一层
要表达的东西。

因此 host 列表是**唯一能覆盖全部情况**的挂载点。FR-060 同时要求证书类原因**与其它原因
可区分**——「关机」和「这台机器的身份变了」共用一句文案，等于把宪法 V 要防的那件事
降级成一次网络故障。

## §2 FR-061：两个 certificate 状态不合并，但分职责

`HostUnreachableReason.certificateRejected` 和 `HostPairingState.certificateChanged`
名字相近，**下一个人的合理动作是把它们合并**。这条明确禁止，并说明为什么。

两者是**因果**不是同义：

| | 是什么 | 生命周期 |
|---|---|---|
| `certificateRejected` | **一次连接尝试的结果** | 派生态，不持久化 |
| `certificateChanged` | **配对关系的状态** | 持久，需要人介入才能离开 |

host 行显示的是**后者**。前者的作用是**触发**后者。

若显示前者，会出现一个具体的坏结果：**一个需要人介入的状态被显示成一闪而过的错误**——
下一次探测（比如主机干脆关机了）会把它换成「不可达」，而证书变更这件事就此消失，
但配对关系其实仍处于被污染的状态。

## 一条方法论记录

这条修正案不是由实现受阻触发的，是由**实现前去找依据**触发的。#35 的三个类型
写得很完整、命名很合理、`certificateRejected` 这个 case 看起来显然该被显示——
**「这个类型存在」和「规格要求这个行为」在读代码时长得一模一样**，而前者不构成后者。

同一天里这个项目已经找到四条「半根线」（写好了但没有对端的实现）。这是第一次
在**动手之前**发现的，代价是一次 grep 而不是一个 PR。
