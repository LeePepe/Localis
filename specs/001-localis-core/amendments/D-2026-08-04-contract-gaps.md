## 0. 一句话

**前三次修正案改的是「契约说什么」；这一次改的是「契约说得对不对」。**

A/B/C 都是在没有实现的前提下写的设计决策。今天两侧第一次**都**有了跑得起来的东西，
于是第一次能拿真实字节去核对契约文本——**四处里有三处是「照字面实现就会坏」**，
只是恰好两侧都没照字面实现，所以至今没出事。**一致是巧合，不是保证。**

| # | 问题 | 性质 | 照字面实现的后果 |
|---|---|---|---|
| **D1** | §3.1 示例不带 `seq`，§3.3 要求每帧必带 `seq` | ⚠️ **自相矛盾** | 发出**无法去重**的内容帧 |

## 1. D1 — §3.1 与 §3.3 自相矛盾（**最急，因为它静默坏事**）

### 1.1 矛盾在哪

**§3.1**（标准 chunk 示例，约 216–225 行）——**不带 `seq`**：

```
data: {"id":"...","object":"chat.completion.chunk","choices":[{"delta":{"content":"He"},"index":0}]}
```

**§3.3**（Amendment C 引入）——**每帧必带 `seq`**：

> **序号**：每个 SSE 事件 **MUST** 带**单调递增**的 `seq`（从 0 开始，**逐 turn** 计数）。

同一份文件里，同一类帧，一个示例说不用带、一条 MUST 说必须带。

### 1.2 为什么这条最急

因为它**坏在最需要它的那类帧上**。

`seq` 是断连续取去重的**唯一**依据——§3.3 的客户端规则写死了「**MUST** 按 `seq` 去重」。
而 §3.1 的示例是**内容 delta**，恰恰是重放边界上**最可能重复、也最不能重复**的一类：
少一个字是缺字，多一个字是重字，两者都直接违反 SC-003「无缺字、无重复」。

一个照 §3.1 字面实现的 bridge 会发出**结构上无法去重的内容帧**。
客户端拿到两份 `"He"`，没有任何依据判断这是重放还是模型真的说了两次。

**现在没出事，只因为实际的 bridge 恰好照 §3.3 写了。** team-lead 实测的真实输出每帧都带
`"seq":0` / `"seq":1` / `"seq":2`…。但那是实现者的判断力，不是契约的保证——
契约给了两个互斥的答案，实现者挑对了一个。**下一个实现者可能挑另一个。**

### 1.3 改法

§3.1 的示例**补上 `seq`**，并在示例下方加一句明确指向 §3.3 的规范条文。

**为什么是改示例、而不是放宽 MUST**：因为 §3.3 那条 MUST 是**对的**——
没有逐帧 `seq`，Amendment C 的整个续取机制不成立。矛盾的两边不是平权的，
§3.1 的示例只是**写于 `seq` 存在之前**的历史残留（`seq` 是 Amendment C 才引入的），
Amendment C 当时没有回头同步这个示例。这是一处**遗漏**，不是一处**设计分歧**。

## 2. D2 — `[DONE]` 物理上带不了 `seq`

### 2.1 问题

`data: [DONE]` 是 SSE 的**字面量**，不是 JSON 对象。**没有地方放 `seq` 字段。**
（它是 OpenAI 基线的一部分，改成 JSON 就不再 OpenAI-compatible，违反本文件的基线约定与宪法 IV。）

于是 §3.3 那条「每个 SSE 事件 **MUST** 带 `seq`」在字面上**不可满足**：
存在一个协议要求发送的事件，它在结构上无法携带该字段。

**一条不可满足的 MUST 比没有规则更糟**——它把「合规」变成不可能，实现者只能各自决定
从哪里开一个没写进契约的口子。目前两侧靠**默契**过关：bridge 的 encoder 在写 `seq` 之前
就 return；iOS 的 mapper 对 `[DONE]` 返回 `seq: nil`。两边猜到了同一个答案，
**但契约一个字都没说**。

### 2.2 改法

§3.3 那条 MUST **加一句显式例外**：`data: [DONE]` 除外，并说明理由（它是字面量不是 JSON）
以及对客户端的后果（**不参与 `seq` 去重与连续性判定**）。

**为什么不改成「`[DONE]` 也要有 seq」**：那需要把 `[DONE]` 变成 JSON，等于放弃 OpenAI 基线。
**为什么不干脆删掉那条 MUST**：见 D1——那条 MUST 是续取机制的地基。
唯一正确的动作是**给一个不可能的情形写明例外**。

### 2.3 顺带：这个例外不留缺口

`[DONE]` 不带 `seq` **不影响**去重的完备性：它是流的终止标记，**不携带任何内容**，
重复收到一个 `[DONE]` 的后果是「流结束」被判定两次——已由 §7 既有条目
「`[DONE]` 后再来数据 → 忽略」覆盖。**没有内容会因此重复或丢失。**

## 3. D3 — `409 session_busy` 没有触发条件

### 3.1 问题

§6 的错误码表列了：

| HTTP | code | 客户端行为 |
|---|---|---|
| 409 | `session_busy` | 提示上一条还没回完 |

但**全文没有任何一处**说 bridge 在什么情况下 **MUST**（或 MAY）返回它。
它是一个只有「收到之后怎么办」、没有「什么时候会收到」的错误码。

### 3.2 实测判据

team-lead 已在真实 bridge 上确认：**同一个 session 并发两个 turn，是两个独立的 claude 进程，
不冲突。** 也就是说，这个错误码所描述的那个冲突**在当前实现下物理上不存在**。

这也与 Amendment C 的语义自洽：C 把 turn 提升为一等公民（`turn_id`、逐 turn 的 `seq`、
逐 turn 的取消与续取）。**turn 才是并发单位，session 只是归位用的容器。**
一个 session 上有两个在跑的 turn，在 C 之后是**结构上合法**的状态。

### 3.3 决定：**标注为「保留未用」，不删除**

两个选项都考虑过，选保留，理由如下（三条，第三条最重要）：

1. **删掉会丢掉答案，只留下问题。** 「同 session 并发要不要报冲突」是一个任何实现者都会
   自然想到的问题。契约里什么都不说，下一个人会重新想一遍，而且很可能得出
   「应该串行化」这个**错误**结论——因为它听起来更安全。写明「已经查过，不冲突」
   是对这个问题的**永久免疫**，删除不是。

2. **删掉会让客户端行为变成未定义。** 该行同时定义了「万一收到 409 怎么办」。
   一个第三方或未来的 bridge 仍可能发它；保留该行意味着客户端有**已定义**的降级路径，
   符合宪法「边界校验 / 不崩溃」。删掉它，收到 409 就成了未定义行为。

3. **本文件已有这个先例。** §3.4(a) 保留了一段被推翻的旧设计并写明「**那是错的，已作废**」，
   而不是静默删除。**记录被否决的选项、连同否决的理由**是这份契约的既有风格——
   它让契约不只是「现在的规则」，也是「为什么不是别的规则」。

**明确不做的事**（team-lead 已点名，此处记录以防日后被「补全」）：
**不为了匹配文档去发明一个人为的冲突条件。** 让实现去迁就一行文档、给一个物理上不存在的
冲突造一个出来，是把因果颠倒。**文档错了就改文档。**

### 3.4 改法

在 §6 表中把该行标为 **[D] 保留未用**，并在表下加一段说明：当前实现下同 session 并发不产生
冲突（turn 才是并发单位），故本码**无触发条件**，bridge **MUST NOT** 为了「用上它」
而人为串行化同 session 的 turn；客户端仍 **MUST** 能安全处理收到它的情况。

## 4. D4 — `max_buffer_bytes` 只有语义、没有接线要求

### 4.1 问题

§2.1 定义了 host 级 `max_buffer_bytes`（「单 turn 缓冲上限」），host 也确实在 `/v1/models`
里发了它（实测 `max_buffer_bytes: 4194304` = 4 MiB）。

但契约**从来没写「客户端 MUST 拿它做什么」**。

于是可以预期的结果发生了：iOS 侧把它解析进了 `HostCapabilities.maxBufferBytes`，
然后**没有任何地方消费它**。一个 host 声明了、客户端解析了、双方都很守规矩、
而这个值**不影响任何行为**——等于没声明。

**一个只被解析、不被消费的协商字段，是一个看起来在协商的假象。**

### 4.2 一处必须先厘清的区分（否则接线会接错）

契约里有**两个不同的字节上限**，此前没有被区分开，很容易被当成同一个：

| | 谁的 | 量的是什么 | 越界后 |
|---|---|---|---|
| **`max_buffer_bytes`**（§2.1） | **host 侧** | **整个 turn** 累积缓冲的上限 | host 截断，续取时标 `truncated`（§3.3） |
| **单帧缓冲上限** | **客户端侧** | **一个尚未终止的 SSE 帧** | 客户端判定流畸形，产生 typed error |

它们不是同一个量，**因此「客户端直接把 `max_buffer_bytes` 拿去当帧上限」是错的**——
那会把一个 turn 级的额度当成帧级的额度。

但两者之间存在一个**真实且严格**的关系：

> **单个帧不可能比整个 turn 的缓冲还大。**

host 声明它整个 turn 最多缓冲 N 字节，那么它**不可能**发出一个大于 N 字节的帧。
所以客户端收到一个超过 N 的未终止帧时，这个流**已经确定是畸形的**——
无需等到自己那个更宽松的默认上限。

这就是这个字段**正确的**消费点：**它是客户端帧上限的上界（收紧，永不放宽）。**

### 4.3 改法

在 §2.1 补一条接线要求：

- host **声明**了 `max_buffer_bytes` → 客户端 **MUST** 用它收紧自己的帧上限
  （取「自身默认」与「host 声明值」中的**较小者**）。**MUST NOT** 忽略它继续用自身默认。
- host **未声明** → 客户端 **MUST** 仍施加一个**有限**的自身上限，**MUST NOT** 无上限读取。
  具体数值**由客户端决定、契约不规定**——它是纯客户端侧的安全网，**从不出现在线上**，
  两侧无需就它达成一致（规定一个数只会制造一个假的互操作要求）。
- 该上限 **MUST NOT** 在客户端硬编码为「协议值」——host 声明了就必须用（宪法 §无硬编码）。

### 4.4 ⚠️ 这一条给别人带来**新活**，不是既有 bug

**必须说清楚**：`SSEParser` 那个 8 MiB 的默认值，在**本修正案之前是完全合规的**——
契约压根没要求客户端消费 `max_buffer_bytes`。它是「没接线」，**不是**「接错了」，
更**不是**谁漏掉了什么。

**本修正案通过之后**，它才从「没接线」变成「违约」。这是**新增约束创造的新工作量**，
时间戳在今天（2026-08-04），责任不在此前的任何实现。

## 5. D5 — 端点清单（编辑性补充）

### 5.1 一处需要更正的前提

本条最初的提法是「`GET /v1/skills` 不在端点清单里」。**核对原文后：这个提法不准确。**
§5 的标题就是 `## 5. Skill 目录 `GET /v1/skills``，与 §1/§2/§3/§4 完全同级同格式。
**它没有被漏掉。**

### 5.2 真正的问题

**这份契约根本没有「端点清单」这个东西。** 端点分散在七个标题里，而且其中一个
**根本不在标题里**——续取端点 `POST /v1/turns/{turn_id}/resume` 只出现在 §3.3 的正文中段，
标题写的是 `### [C] 3.3 续取 \`x-localis-resume-from\``（一个**头名**，不是路径）。

结果：想知道「这个协议一共有几个端点」，唯一办法是通读全文。
对一份被两个独立实现当作**唯一真源**的契约来说，这是个真实的缺陷——
今天两侧首次比对时，正是靠人工通读才确认了端点集合。

### 5.3 改法

在 §0 之后加一张 **[D] 端点清单**表，一次列全七个端点（含 `/v1/skills` 与那个此前无标题的
`resume`），每个给出方法、路径、所属小节、以及是否由能力位门控。
**这是编辑性补充，不改变任何端点的语义。**

## 6. 合宪性

| 原则 | 结论 |
|---|---|
| **I. 密钥零上设备** | ✅ 无新增数据面。`seq` 是元数据（Amendment C 已论证）；端点清单是纯编辑性 |
| **II. Swift 6 并发** | ✅ 不涉及。D4 影响 `SSEParser` 的一个上限取值，`SSEParser` 已是值类型 |
| **III. SPM 分层** | ✅ 不新增包。D4 的落点在 TransportKit（协议层），不跨层 |
| **IV. 单一协议** | ✅ **正向强化**。D2 显式保护了 OpenAI 基线（拒绝把 `[DONE]` JSON 化）；D3 拒绝为一行文档发明冲突条件；D4 把一个被硬编码的值改为**从 host 读**——正是「能力是数据」 |
| **V. TLS + 配对** | ✅ 不涉及鉴权面。D4 收紧了一个资源上限，**只收紧不放宽**，是安全侧的改进 |
| **VI. 不可变** | ✅ 不涉及 |
| **VII. 范围克制** | ✅ 不新增 target、不新增端点。D5 只是把**已存在**的端点列出来 |

**无违宪项。** 本修正案**不改变任何协议语义**，因此**协议版本仍为 `1`**：
D1/D2/D5 是把契约文本改成与**两侧既有实现**一致（实现没变，只是文本终于说对了）；
D3 是标注；**只有 D4 新增了一条客户端侧约束**，且它只收紧客户端自身的安全上限，
线上字节**一字不变**——老 bridge 与老客户端互操作性完全不受影响。
